# 1.2.0 优化说明

日期：2026-10-29。

本轮只做三件事：**把最热的搜索路径提速近一倍**、**让连续吸色不再排队等算**、
**修掉一个让主标题样式从未生效的界面缺陷**。所有改动都以「输出逐位不变」为前提。

> 完整的 20 轮迭代记录（含逐轮目标、改动、理由与自检）见
> [ITERATION_2026-10-29.md](ITERATION_2026-10-29.md)。本文只讲性能这一条主线。

## 一、配方搜索提速（suggest ×9.7）

`suggest` 原本单次约 120 ms（CIEDE2000 / 默认 6 条建议 / 5 个首选品牌），
其中 **81% 花在双色搜索**上：每个锚点 16 条候选 → 120 个色号对 × 38 次 ΔE 评估。

### 1. 色号对跨锚点复用（`recipe_engine._best_pair` 的 `cache`）

同一次 `suggest` 里会为多个锚点各解一次配方，而 `_pool_for` 只是把锚点换到队首，
同一品牌下各锚点的候选池**高度重叠**：实测 720 个「色号对槽位」里只有 360 个是
不同的。现在把双色搜索结果按 `(uid_i, uid_j)` 缓存在调用方（`PaintMatcher.suggest`
持有，生命周期 = 一次 suggest），跨锚点直接复用。

> 缓存键是**有顺序**的 uid 对，不是排序后的无序对。原因是细化阶段是「边走边移动
> 中心」的局部搜索，结果与顺序有关（A→B 与 B→A 会落到不同局部点，ΔE 相差可达
> 1e-3）。按无序对缓存会悄悄改掉配方结果，宁可少命中也不改数。

### 2. 细化阶段剪枝（`_PAIR_REFINE_MARGIN`）

粗扫 21 档之后，若该色号对的粗扫最优点已经比当前最优差出 1.5 ΔE 以上，就跳过
细化（17 次评估）。细化窗口只有半个粗格，ΔE 在其中近似二次型，改善量被曲率限制
在远小于 1.5 的范围内，因此这条剪枝不改变任何结论——`tests/test_search_cache.py`
里有一条把余量调到 `inf`（等于不剪枝）再逐位比对的回归测试。

被剪掉的细化评估占双色搜索总量的 **约 85%**（从每对 38 次降到多数情况 21 次）。

### 3. 替代色检索的亮度下界剪枝

CIEDE2000 有严格下界 `ΔE ≥ |ΔL| / S_L`（交叉项满足 `x²+y²+R_T·x·y ≥ 0`）。
`alternatives._nearest` 先按 `|ΔL| / S_L,max > tolerance` 排除，再算完整 ΔE：
容差 3.0 时 |ΔL| 允许范围只有 ±5.2，全库绝大多数色号被直接排除。
`delta_e.sl_scale_max()` 提供各公式的 S_L 上界，`tests/test_delta_e.py` 里有一条
与「不剪枝的暴力实现」逐位对照的等价性测试。

### 4. 跨调用搜索缓存

缓存内容（某个色号对/三元组的最优配比）只取决于**目标色 + 混合模型 + 色差公式**，
与容差、总滴数、候选池组成都无关，因此可以从「一次 suggest 内」抬到
`PaintMatcher` 上、跨多次调用复用。收益最明显的是「用量参数」页：拖面积/层数/稀释比
会触发整段重算，但搜索输入一个字都没变——**单次重算从 67 ms 降到 3.1 ms**。

只保留最近一个目标色的缓存，换目标色整体丢弃，内存有界；多线程下每次调用持有自己
那份 dict 的引用，最坏只是少命中，不会读到别人的缓存。

### 5. 双色粗扫向量化（numpy）

双色粗扫是「120 个色号对 × 21 档配比」的规则网格，正好适合批量数组运算：
`app/services/vector_scan.py` 把整池铺成 `(120, 21, 3)` 一次算完
「K/S 加权 → 反射率 → XYZ → Lab → CIEDE2000」，**粗扫本身快 10.9×**。

数值上刻意与标量实现逐步对齐：720 个色号对的最优配比完全一致，ΔE 最大差 3.9e-14。
numpy 缺失或公式不是 CIEDE2000 时返回 `None`，调用方回退标量路径。

> 三色粗扫**不是直接向量化**：三色权重网格里有大量近平局，1e-14 的差异会改变
> `argmin` 选中的网格点，最终换掉配方里的一支漆（68 块指纹里 6 块变化）。现在改成
> 「向量化筛出所有可能是最优的网格点（±1e-9）+ 标量按原顺序裁决」，速度拿到了，
> 平局规则没变。

### 6. ΔE 公式解析提到循环外

`rank_by_distance` / `closest_entries` / `alternatives._nearest` 三处都在按全库条数
（672）跑的循环里调用 `delta_e(..., formula)`，每次都要做一遍
`upper() + replace()` 字符串处理。改为循环外 `resolve_delta_e(formula)` 解析一次。

### 实测（`python scripts/bench.py`，3 次中位数）

| 项目 | 优化前（1.1.0） | 优化后（1.2.0） | 变化 |
| --- | --- | --- | --- |
| `delta_e_2000` ×200k | 0.410 s | 0.42 s | 持平（公式未动） |
| `suggest` ×50 | 6.071 s | 0.624 s | **−90%（9.7×）** |
| 五瓶调配 `base_mix` ×20 | 2.066 s | 0.916 s | −56% |
| 方案展开 `scheme` ×20 | 2.156 s | 0.398 s | −82% |
| 同目标重算 ×20（`repeat`） | — | 0.063 s | 单次 3.2 ms |
| 单次 suggest | ≈121 ms | **12.5 ms** | |

### 结果一致性怎么保证

不是「看起来差不多」，是逐位比对：固定 45 个目标色 × 3 套色差公式（CIEDE2000 /
CIE94 / CMC），各跑一遍建议列表，再跑五瓶基础漆调配与方案页，把
「锚点 / 配方组分 / 滴数 / 比例 / 混合色 / ΔE / 替代色」全部落成 JSON 对比：

```
147 个结果块，优化前后 diff = 0
```

脚本思路见 `tests/test_search_cache.py`（同款断言已固化成回归测试）。

## 二、连续吸色不再排队（`async_suggest._LatestSequence`）

原本「去抖」只发生在**结果端**：每个任务带 token，渲染时只采纳最新一次的结果，
旧任务算完就被丢弃。但**旧任务照样要算**——线程池里堆十几个陈旧任务时，最新
一次的结果仍排在它们后面，界面看起来就是卡住。

现在排队中的任务会在**开工前**检查自己是否已被后来的请求取代，是则直接返回，
连 `matcher.suggest` 都不调用。

序号由 `_LatestSequence` 单调发放，**不与窗口的 token 比较大小**：token 由各窗口
自己从 0 开始计数，换一个窗口就会回退，按大小比较会把新窗口的第一次计算误判成
过期（界面永远停在「计算中」）。判据是「序号相等」而非「大小关系」。

## 三、修复：主标题样式从未生效（`ui/main_window.py`）

```python
title.setObjectName("TitleLabel")      # 15pt / 600
title.setObjectName("SectionLabel")    # ← 紧接着被覆盖成 10pt
```

`theme.py` 里 `QLabel#TitleLabel`（15pt）与 `QLabel#SubTitleLabel`（9pt）从来没被
用上，窗口标题实际按 10pt 正文渲染，副标题也丢了字号。删掉后两行覆盖即可。
`docs/screenshots/` 与 `scripts/screenshot.py` 的产出需重拍核对。

## 五、已知未做

- **`scheme_engine` 的 7 种配色方案（互补/三角/邻近…）目前没有界面入口**：
  `build_scheme` / `submit_scheme` 只有测试在用，「基础配色」页展示的是五瓶基础漆
  调配。要么补一个入口，要么删掉这套代码——需要产品决策，本轮没动。
- **`_best_triple` 未接入缓存**：它的结果依赖 `current_best`（剪枝上界），跨锚点
  复用的语义不干净；目前它只占 suggest 的 13%，收益不足以抵消复杂度。
- **向量化重写 ΔE 内层循环**（numpy 批量算 120 个色号对）理论上有 5–10× 空间，
  但会引入 ULP 级差异，与「逐位不变」的验收标准冲突，暂不做。
